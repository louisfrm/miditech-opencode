Tâche 01 · Préparer

Démarrer sur le fork

Travaillez dans le dépôt d'exercice ; gardez le serveur de développement séparé d'OpenCode.

  1. Clonez le dépôt d’exercice et ouvrez sa racine.
    git clone https://github.com/louisfrm/agents.md-part2.git
cd agents.md-part2
git status --short
  2. Installez les dépendances et démarrez le site dans un terminal.
    npm install
npm run dev
  3. Dans un second terminal à la même racine, lancez OpenCode.
    opencode

Tâche 02 · Configurer

Créer la configuration projet

Placez les réglages OpenCode dans le dépôt pour que l'équipe puisse les relire.

  1. Dans la racine de votre fork agents.md (le dossier contenant package.json et AGENTS.md), créez opencode.json avec le contenu ci-contre.
  2. Au même endroit, créez les dossiers .opencode/agents/, .opencode/commands/ et .opencode/skills/.
  3. Laissez ces dossiers vides pour le moment : vous ajouterez les fichiers dans les tâches suivantes.

opencode.json

{
  "$schema": "https://opencode.ai/config.json",
  "agents": {
    "build": {
      "description": "Développe le site agents.md et délègue les audits"
    }
  }
}

build est l’agent principal intégré. Aucun modèle n’est imposé par le projet.

Tâche 03 · Contrôler

Limiter les permissions du développeur

Autorisations courantes sans friction ; autres commandes sur demande ; publication et suppression bloquées.

  1. Remplacez opencode.json par la version ci-contre.
  2. Demandez à build d’exécuter git status : autorisation automatique.
  3. Demandez git log -1 : OpenCode doit demander votre accord.
  4. Demandez git push pour vérifier le blocage. Ne lancez pas vous-même la commande.

La dernière règle correspondante gagne. Ces permissions contrôlent les outils d’OpenCode.

opencode.json · version à conserver

{
  "$schema": "https://opencode.ai/config.json",
  "agents": {
    "build": {
      "description": "Développe et délègue les audits",
      "permissions": [
        { "action": "edit", "resource": "*", "effect": "allow" },
        { "action": "shell", "resource": "*", "effect": "ask" },
        { "action": "shell", "resource": "git status *", "effect": "allow" },
        { "action": "shell", "resource": "git diff *", "effect": "allow" },
        { "action": "shell", "resource": "npx tsc --noEmit", "effect": "allow" },
        { "action": "shell", "resource": "node --test workshop/redirect.test.mjs", "effect": "allow" },
        { "action": "shell", "resource": "git push *", "effect": "deny" },
        { "action": "shell", "resource": "rm *", "effect": "deny" },
        { "action": "shell", "resource": "Remove-Item *", "effect": "deny" },
        { "action": "skill", "resource": "secure-code-review", "effect": "deny" },
        { "action": "subagent", "resource": "*", "effect": "deny" },
        { "action": "subagent", "resource": "security-reviewer", "effect": "allow" }
      ]
    }
  }
}

Tâche 04 · Spécialiser

Créer le subagent de sécurité

Le reviewer lit et cherche, mais ne peut ni modifier les fichiers ni lancer un shell libre.

  1. Créez .opencode/agents/security-reviewer.md.
  2. Fermez OpenCode, puis relancez opencode depuis la racine du fork pour charger le nouvel agent.
  3. Dans un autre terminal à la racine du fork, lancez opencode debug agents : security-reviewer doit figurer dans la liste.
  4. Comparez ses permissions à celles de build.

general et explore sont des subagents intégrés. La liste montre les agents chargés ; les permissions de build déterminent lesquels il peut appeler. Si votre agent manque, vérifiez le nom et le chemin de son fichier.

.opencode/agents/security-reviewer.md

---
description: Audite la sécurité du diff sans modifier les fichiers
mode: subagent
permissions:
  - action: edit
    resource: "*"
    effect: deny
  - action: shell
    resource: "*"
    effect: deny
  - action: shell
    resource: "git status --short"
    effect: allow
  - action: shell
    resource: "git diff -- ."
    effect: allow
  - action: subagent
    resource: "*"
    effect: deny
  - action: skill
    resource: "*"
    effect: deny
  - action: skill
    resource: secure-code-review
    effect: allow
  - action: read
    resource: "*.env"
    effect: deny
  - action: read
    resource: "*.env.*"
    effect: deny
  - action: read
    resource: "*.env.example"
    effect: allow
  - action: external_directory
    resource: "*"
    effect: deny
---

Tu es reviewer sécurité du dépôt agents.md.
Lis le diff et le contexte utile. Ne modifie rien.
Ne signale que les risques introduits par le diff.
Pour chaque constat : gravité, fichier/ligne, preuve,
impact, correction minimale. Termine par un verdict.

Tâche 05 · Déléguer

Déléguer une première revue

L'agent principal fournit un contexte précis au reviewer, qui répond depuis une session enfant.

  1. Rendez les fichiers nouveaux visibles à git diff avec une intention d’ajout.
    git add -N opencode.json .opencode/agents/security-reviewer.md
git diff -- opencode.json .opencode/agents/security-reviewer.md
  2. Dans OpenCode, sélectionnez build et envoyez le prompt ci-contre.
  3. Ouvrez la session enfant ; vérifiez qu’aucun fichier n’a été modifié.

Prompt à coller

Demande au subagent security-reviewer d'auditer uniquement
le diff de opencode.json et de .opencode/agents/security-reviewer.md.

Cette première délégation porte sur la configuration et montre les permissions du subagent en action.

Tâche 06 · Outiller

Ajouter le Skill du projet

Le reviewer charge une méthode de sécurité adaptée au code Next.js du dépôt.

  1. Créez .opencode/skills/secure-code-review/SKILL.md.
  2. Dans OpenCode, demandez au reviewer de charger ce Skill.
  3. Vérifiez l’appel à l’outil skill dans la session enfant.

Seul le reviewer peut charger ce Skill via l’outil skill. Ce réglage montre une délégation spécialisée ; il n’empêche pas build de lire le fichier.

.opencode/skills/secure-code-review/SKILL.md

---
name: secure-code-review
description: Audit sécurité ciblé d'un diff TypeScript et Next.js
---

# Méthode
1. Lire le diff ; auditer seulement les changements.
2. Repérer les entrées : query, body, headers.
3. Vérifier validation, injection, redirections.
4. Examiner secrets, authentification, autorisation.
5. Examiner logs, erreurs, réseau, dépendances.
6. Confirmer le chemin d'exploitation de chaque risque.
7. Rendre gravité, preuve, impact, correction minimale.
8. Dire si aucun risque introduit n'est confirmé.

Ne modifie pas le code.

Tâche 07 · Automatiser

Créer /security-review

Transformez la revue ponctuelle en commande qui fournit automatiquement le diff au subagent.

  1. Créez .opencode/commands/security-review.md.
  2. Dans OpenCode, lancez /security-review sur le diff de configuration.
  3. Vérifiez le format du rapport rendu à l’agent principal.

Les commandes dans .opencode/commands/ sont chargées automatiquement : lancez /security-review sans redémarrer OpenCode. Pour tout nouveau fichier : git add -N chemin/du/fichier avant la revue.

.opencode/commands/security-review.md

---
description: Audite la sécurité des changements courants
agent: security-reviewer
subagent: true
---

Charge le Skill secure-code-review avec l'outil skill.
Exécute `git status --short` et `git diff -- .`.
Limite l'analyse aux changements du diff.
Lis le code voisin seulement pour confirmer un constat.
Réponds avec : verdict, constats par gravité,
preuves fichier/ligne, corrections minimales.
Ne modifie aucun fichier.

Le reviewer lance ces commandes avec ses propres permissions ; subagent: true lui donne un contexte distinct.

Tâche 08 · Planifier

Créer /prime et /plan-feature

Préparez un état des lieux réutilisable avant de planifier un changement.

  1. Créez les deux commandes ci-contre.
  2. Lancez /prime : vérifiez qu’il résume l’état Git, les commandes déclarées et les contraintes d’AGENTS.md sans lancer de test.
  3. Ne lancez pas encore /plan-feature : la demande à planifier arrivera à la tâche 11, après le patch et sa première revue à la tâche 10.

/prime prépare la session ; le test ciblé et le plan de correction viennent plus loin.

.opencode/commands/prime.md

---
description: Prépare une session sur le dépôt courant
---

Lis AGENTS.md s'il existe et le manifeste principal du projet
(par exemple package.json ou pyproject.toml). Ne parcours pas
tout le dépôt. Exécute `git status --short --branch`.

Résume brièvement :
1. le rôle du dépôt et les fichiers d'entrée utiles ;
2. la branche et les changements en cours ;
3. les commandes de développement et de vérification
   explicitement déclarées ou recommandées ;
4. les contraintes à respecter pour la prochaine tâche.

Distingue les contrôles disponibles de ceux effectivement lancés.
N'exécute aucun test, n'installe rien et ne modifie aucun fichier.
Si une information manque, indique-le sans l'inventer.

.opencode/commands/plan-feature.md

---
description: Prépare un plan court pour un changement ciblé
agent: build
---

Demande : $ARGUMENTS
Lis AGENTS.md et le code touché. Écris un plan dans
workshop/plan.md : objectif, fichiers, étapes, risques,
validation exécutable, critères d'acceptation.
Ne modifie aucun autre fichier et n'implémente rien.

Tâche 09 · Préparer l’exécution

Créer /execute

Le plan relu servira ensuite de contrat d'implémentation : code, validation, rapport des écarts.

  1. Créez .opencode/commands/execute.md.
  2. Relisez le texte de cette commande : il doit prévoir la lecture de workshop/plan.md avant d’implémenter, respecter AGENTS.md et éviter npm run test, absent du dépôt.
  3. Gardez npm run dev ouvert : le test HTTP du scénario en dépend.

workshop/plan.md n’existe pas encore : /plan-feature le créera à la tâche 11. Lancez /execute seulement après avoir relu ce plan.

.opencode/commands/execute.md

---
description: Exécute le plan relu et valide le changement
agent: build
---

Lis le fichier workshop/plan.md, puis applique-le dans l'ordre.
Respecte AGENTS.md. Ne lance pas `npm run build`.
Exécute les validations prévues. Si une validation échoue,
répare puis relance-la. N'utilise pas `npm run test` :
ce script n'existe pas dans ce dépôt.
Rends un rapport : fichiers, résultats, écarts
au plan et points à faire auditer.

Tâche 10 · Auditer

Introduire et auditer le scénario

workshop/scenario.patch est une contribution simulée : il ajoute une route API qui redirige vers la valeur du paramètre to. Inspectez le changement avant de le corriger.

  1. Appliquez le patch fourni. Il crée pages/api/go.ts.
    git apply --check workshop/scenario.patch
git apply workshop/scenario.patch
git add -N pages/api/go.ts
git diff -- pages/api/go.ts
  2. Contrat attendu : GET /api/go?to=/examples redirige vers une page locale.
  3. Lancez /security-review. Relevez la ligne dangereuse et un exemple exploitable.
  4. Gardez le rapport : il servira à /plan-feature à la tâche 11.

git apply --check vérifie le patch sans changer les fichiers ; git apply le pose ; git add -N montre le nouveau fichier dans git diff, sans indexer son contenu.

Indice après votre revue

to vient de la requête et arrive directement dans res.redirect : c’est une redirection ouverte.

Exemple : /api/go?to=https%3A%2F%2Fexample.net%2Flogin.

workshop/redirect.test.mjs contient les critères comportementaux, sans fournir la correction.

Tâche 11 · Intégrer

Planifier, corriger, revérifier

Orchestrez build et security-reviewer jusqu'à un diff validé et une revue finale.

  1. Après la première revue de la tâche 10, lancez /plan-feature avec la demande ci-contre. Relisez workshop/plan.md : les URL externes, // et les chemins avec barre oblique inversée doivent être couverts.
  2. Lancez /execute, npm run dev toujours actif.
  3. Exécutez les validations si l’agent ne l’a pas fait. Les tests de refus échouent avant correction et réussissent après.
    npx tsc --noEmit
node --test workshop/redirect.test.mjs
git diff --check
git diff -- pages/api/go.ts workshop/plan.md
  4. Relancez /security-review, examinez le diff, puis créez un commit si tout est bon.

Dans OpenCode

/plan-feature Sécuriser GET /api/go : n’accepter que des chemins locaux commençant par un seul / et sans barre oblique inversée ; rediriger vers / pour toute autre valeur. Préserver le statut 307 et faire passer workshop/redirect.test.mjs.
/execute
/security-review

Attendu : /examples accepté ; https://example.net/login , //example.net/login et /\example.net/login renvoient vers /. Autre port : définir TP_BASE_URL.

Bonus facultatif

Journaliser les commandes shell

Un plugin local peut observer les commandes de l’outil shell.

  1. Créez .opencode/plugins/shell-audit.js à la racine du fork.
  2. Lancez opencode reload dans un terminal à la racine du fork, puis demandez à build d’exécuter git status.
  3. Dans PowerShell, affichez le journal avec Get-Content .opencode/shell-audit.log -Tail 10.
  4. Option : limitez le journal aux commandes Git en ajoutant if (!event.command.trim().startsWith("git ")) return; au début du callback. Rechargez OpenCode et vérifiez le résultat.

Pour interdire une commande connue, utilisez une règle deny dans opencode.json. Le fichier *.log est ignoré par Git ; évitez d’y inscrire des secrets.

.opencode/plugins/shell-audit.js

import { appendFile } from "node:fs/promises";

const logFile = new URL("../shell-audit.log", import.meta.url);

export default {
  id: "workshop.shell-audit",
  async setup(ctx) {
    await ctx.shell.hook("create.before", async (event) => {
      await appendFile(logFile, `${new Date().toISOString()}\t${event.command}\n`, "utf8");
    });
  },
};

ctx.shell.hook("create.before", ...) reçoit la commande avant son exécution.

Bonus facultatif

Brancher une documentation au projet

Ajoutez à l’environnement du fork un serveur MCP de documentation, puis utilisez-le pour vérifier l’API Next.js du scénario.

  1. Depuis la racine du fork agents.md, lancez les commandes ci-contre. Sans --global, le serveur est inscrit dans la configuration du projet.
  2. Dans opencode.json, vérifiez que context7 apparaît sous mcp.servers, en conservant agents et ses permissions. opencode mcp list doit indiquer connected.
  3. Dans OpenCode, ouvrez /mcps, puis envoyez le prompt ci-contre à build. Vérifiez dans la trace qu’il interroge Context7 et cite la documentation obtenue.

La connexion nécessite Internet. L’usage de base de Context7 ne demande pas de clé API ; si OpenCode affiche needs authentication, suivez le parcours proposé dans /mcps. La syntaxe OpenCode V2 est mcp.servers.

Dans le terminal du fork

opencode mcp add context7 --url https://mcp.context7.com/mcp
opencode mcp list

Extrait attendu de opencode.json

"mcp": {
  "servers": {
    "context7": {
      "type": "remote",
      "url": "https://mcp.context7.com/mcp"
    }
  }
}

Dans OpenCode

Utilise Context7 pour retrouver la documentation Next.js 16 de res.redirect dans une API Route du Pages Router. Explique la signature utilisée dans pages/api/go.ts, cite ta source et ne modifie aucun fichier.
